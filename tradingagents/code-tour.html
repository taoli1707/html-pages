What happens inside TradingAgents when you run it for one ticker on one date?

Written 2026-10-08 · Main path: about 25 minutes · Complete page: about 40 minutes · You need to know: Python, and what a large language model is

The short answer

TradingAgents is a Python program that asks a language model to play 12 roles about one stock on one date. The roles form a graph. Four analysts work at the same time. Then two researchers debate, a manager decides, a trader proposes, three risk analysts debate, and a portfolio manager rates. The rating is one of five words: Buy, Overweight, Hold, Underweight, Sell.

With the default settings, one run executes 13 graph nodes. First 5 at the same time: 4 analysts and 1 memory step. Then 2 researcher turns, 1 manager, 1 trader, 3 risk turns, and 1 portfolio manager. The data layer never serves data after the analysis date.

The code has 12,657 lines of Python in the packages tradingagents and cli, and 13,683 lines of tests.

Assumptions on this page
  • The example run uses the default settings: OpenAI, deep model gpt-6-sol, quick model gpt-6-luna, all four analysts, one round for each debate.
  • The example run was followed by hand, not run. This computer has Python 3.9.6, the package needs 3.11 or later, and there is no API key. The page shows what the code computes without a model: the order of the nodes, the counters, and the dates.
  • The code is at commit 1394a3f, release 0.6.0. The working copy has one uncommitted file, CLAUDE.md, which is documentation only.

Part A: the run, from a ticker and a date to a decision

The short answer for part A

The class TradingAgentsGraph builds a LangGraph graph one time. A run passes one dictionary, the state, through the nodes. Each node reads the state, calls a chat model, and returns the fields that it changed. Two counters in the state end the debates.

1. One run followed by hand: 13 node executions turn NVDA and 2026-09-23 into a rating

You run this command in a terminal, with an OpenAI key in the file .env:

tradingagents --ticker NVDA --date 2026-09-23 --save --no-show

The ticker is NVDA, the stock of NVIDIA. The trade date (the date of the analysis, called trade_date in the code) is 23 September 2026. The command then asks four questions, and on this page the answers are the defaults. The questions are the provider (the company or server that runs the chat model), the two models, the depth of the debates, and the language.

Worked example, followed by hand, not run
  1. The command builds a TradingAgentsGraph (tradingagents/graph/trading_graph.py:55). The constructor creates two chat models (lines 79 and 80): the deep model gpt-6-sol and the quick model gpt-6-luna. These are the two model tiers (tradingagents/default_config.py:92 to 94). The quick tier serves the analysts, researchers, risk analysts and trader. The deep tier serves the two managers.
  2. The function _validate_trade_date (trading_graph.py:30) checks the date. It must have the form YYYY-MM-DD, and it must not be after today (line 39). On 8 October 2026 the date 2026-09-23 passes. A date in the future would raise ValueError before any model call.
  3. The run builds its first state (the one dictionary that the graph passes from node to node, class AgentState in tradingagents/agents/state.py:45). create_initial_state (tradingagents/graph/propagation.py:13) fills it: the ticker, the trade date, four empty report fields, two debate counters at 0. First, resolve_instrument_context (trading_graph.py:117) asks Yahoo Finance for the company name, sector and exchange of NVDA. This instrument context reaches every prompt, so no agent invents another company from the price chart.
  4. The graph starts five nodes at the same time: Market Analyst, Sentiment Analyst, News Analyst, Fundamentals Analyst, and Memory Log (tradingagents/graph/setup.py:160 to 165). A node is one step of the graph: a function that reads the state and returns the fields that it changes. Each analyst runs inside its own analyst subgraph (a small graph with a private message history, built by _analyst_graph, setup.py:53). The subgraph returns only the report of its analyst, so four analysts never write the same field. The Memory Log node reads the memory log (a text file with one entry per past decision) and settles past decisions (trading_graph.py:308).
  5. Inside the Market Analyst, the model calls a tool (a Python function with a description that the model can read and call). The model chooses the arguments. The Market Analyst has 3 tools: price data, one technical indicator, and a verified snapshot (tradingagents/agents/analysts/market_analyst.py:8). Each tool round (one answer of the model that asks for tools, followed by their results) is the step pair agent → tools → agent. After 20 rounds the subgraph sends the model a final message and takes its report, whatever it answers (setup.py:76 to 88).
  6. The Bull Researcher starts only when all five nodes have finished (setup.py:166). It writes its argument into the debate state with the prefix "Bull Analyst:" and raises the counter from 0 to 1 (tradingagents/agents/researchers/bull_researcher.py:53 and 60). should_continue_debate (tradingagents/graph/conditional_logic.py:16) decides the next node. The counter 1 is below 2 × 1 = 2, and the response starts with "Bull", so the Bear Researcher is next. A debate round is one turn of each side; max_debate_rounds = 1 gives 2 turns.
  7. The Bear Researcher raises the counter to 2. The same function sees 2 ≥ 2 and sends the run to the Research Manager.
  8. The Research Manager (deep tier) reads the debate and returns a plan with a recommendation on the five-word scale. The plan goes into the field investment_plan. This agent uses structured output: the model fills a typed object (class ResearchPlan, tradingagents/agents/schemas.py:95) instead of free text. A provider without this feature gets a free-text prompt (tradingagents/agents/structured.py).
  9. The Trader (quick tier) turns the plan into a transaction proposal (tradingagents/agents/trader/trader.py). The proposal has an action Buy, Hold or Sell, and when possible an entry price and a stop-loss price.
  10. The Aggressive Analyst sets latest_speaker to "Aggressive" and raises the risk counter to 1 (tradingagents/agents/risk_mgmt/aggressive_debator.py:57 and 63). should_continue_risk_analysis (conditional_logic.py:26) sees 1 below 3 × 1 = 3 and the speaker "Aggressive", so the Conservative Analyst is next. Then the counter is 2 and the Neutral Analyst is next. Then the counter is 3, and 3 ≥ 3 sends the run to the Portfolio Manager.
  11. The Portfolio Manager (deep tier) returns a PortfolioDecision object. Its field rating becomes the field final_rating of the state (tradingagents/agents/managers/portfolio_manager.py:83). The rating is one of five words: Buy, Overweight, Hold, Underweight, Sell. If structured output fails, parse_rating reads the rating from the text (line 86). When it finds none, the result is REVIEW: a person must read the decision (tradingagents/agents/rating.py:96).
  12. The graph ends. The command records the decision (trading_graph.py:358): a JSON file with the full state, and one new entry in the memory log. The flag --save writes the reports to a folder; part C lists the files.

Result: 13 node executions: 5 at the same time, then 2, 1, 1, 3, 1. The rating is in final_rating. The number of model calls is larger: each tool round of an analyst is one more call.

2. The rule: one state dictionary, parallel analysts, and two counted debates

The graph is built one time in GraphSetup.setup_graph (setup.py:109).

Two functions decide the arrows with a condition. LangGraph calls such a function a conditional edge (a function that reads the state and returns the name of the next node). The table lists all their rules.

How to read this table: find the node that just finished, and read its rows from top to bottom. The first true condition gives the next node. Rows 1 to 7 are conditional_logic.py:16 to 33; rows 8 and 9 are setup.py:48 and 77.

The subgraph has an output schema with one field: the report of this analyst (setup.py:62 and 63). So the messages of the Market Analyst never reach the state of the main graph.

3. Wrong idea corrected: the agents do not share one conversation

Common wrong idea

Wrong: "The 12 roles are 12 messages in one long chat. Every agent sees everything that every earlier agent said, and every tool result."

Correct: each agent sees only what its node function puts into its prompt. The Bull Researcher receives the four reports, the debate history, and the last Bear argument (bull_researcher.py:12 to 45). The Portfolio Manager receives the plan, the proposal, the risk debate, and the lessons (portfolio_manager.py:42 to 76). No agent after the analysts sees a tool result.

Why the wrong idea fails: the state field messages exists. But each analyst subgraph keeps its own copy and returns only its report (setup.py:62). The later agents build a new prompt from the named fields of the state. If an analyst was not selected, its report field is empty. Then the prompt says "No market report in this run: it is not available, not an empty finding" (context.py:190 to 201). So the model does not invent the report.

4. More detail: one debate round makes 2 researcher turns, two rounds make 4

The two settings max_debate_rounds and max_risk_discuss_rounds do not add nodes to the graph. They change the two counters in the table above.

One round (the default)

Research debate: the counter stops at 2 × 1 = 2. Turns: Bull, Bear.

Risk debate: the counter stops at 3 × 1 = 3. Turns: Aggressive, Conservative, Neutral.

Node executions: 13.

Two rounds

Research debate: the counter stops at 2 × 2 = 4. Turns: Bull, Bear, Bull, Bear.

Risk debate: the counter stops at 3 × 2 = 6. Turns: the same three, two times.

Node executions: 5 + 4 + 1 + 1 + 6 + 1 = 18.

The principle: the number of turns is 2 × max_debate_rounds for the researchers and 3 × max_risk_discuss_rounds for the risk analysts. Each turn is one model call. In the second round, the Bull Researcher receives the whole debate history and the last Bear argument (bull_researcher.py:12 to 18). So the second turn is a reply, not a repeat.

Part B: the data, from a tool call to a data source

The short answer for part B

An analyst calls a tool in tradingagents/agents/tools.py, which clamps every date to the trade date. Then the router in tradingagents/dataflows/router.py tries only the data sources that the settings name, in that order. A failure never ends the run: the tool returns a fixed text that says the data is unavailable.

6. One tool call followed by hand: a window that ends on 1 October is moved back to end on 23 September

In the run of part A, the Market Analyst asks for price data. Suppose the model asks for a window after the trade date, because it takes the real date of today as "now".

Worked example, calculated with a copy of the two date functions
  1. The model calls get_stock_data(start_date="2026-09-25", end_date="2026-10-01"). The tool receives two more arguments that the model cannot set: the ticker and the trade date. Both are injected from the state (tools.py:19 to 23). The trade date is 2026-09-23. The annotation InjectedState tells LangGraph to take the value from the state, and the model never sees it.
  2. The tool calls as_of_window("2026-09-25", "2026-10-01", "2026-09-23") (tools.py:35; the function is in tradingagents/dataflows/date_window.py:91). First the end: as_of (line 78) returns the date that the model asks for, but never later than the trade date. 1 October is after 23 September, so the end becomes 2026-09-23.
  3. The end changed, and the start 2026-09-25 is after the new end 2026-09-23. So the window keeps its length and moves back. The length is 1 October minus 25 September = 6 days. The new start is 23 September minus 6 days = 2026-09-17. Lines 104 to 106. Otherwise the start would be after the end. I checked the result ("2026-09-17", "2026-09-23") with a copy of the function under Python 3.9.
  4. The tool calls route_to_vendor("get_stock_data", "NVDA", "2026-09-17", "2026-09-23") (router.py:200). The router finds the category of the method: get_stock_data is in core_stock_apis (router.py:46 to 51). A vendor is an external data source with its own module under tradingagents/dataflows/vendors/. A category is a group of tool methods that share one vendor setting. There are six: prices, technical indicators, fundamentals, news, macro data, prediction markets.
  5. The router reads the setting for the category (get_vendor, line 160). The dictionary tool_vendors has no entry for this method, so the category setting applies: data_vendors["core_stock_apis"] = "yfinance" (default_config.py:159). The setting is the vendor chain: a list of vendor names, separated by commas, in the order to try. This chain has one vendor, Yahoo Finance, through the library yfinance.
  6. The router finds the function for this vendor in VENDOR_METHODS (router.py:99 to 102): get_YFin_data_online (vendors/yahoo/market.py:18). It asks yfinance for the rows from 17 September to 23 September, plus one day, because yfinance excludes the end date (lines 33 and 34).
  7. If Yahoo answers with rows, the router returns them as text (router.py:236). If Yahoo answers with nothing, the function raises NoMarketDataError. If Yahoo cannot be reached, it raises VendorUnavailableError (vendors/yahoo/common.py:17 to 24).

Result: the model asked for 25 September to 1 October and received 17 September to 23 September.

7. The rule: the router tries only the configured vendors, and every failure becomes a typed error or a sentinel

The code is in layers.

Every vendor function reports a failure with one of three exception classes (tradingagents/dataflows/errors.py).

Three error classes tell the router three different facts about a failed vendor
Error classMeaningWhat the router does
NoMarketDataErrorThe vendor answered, and it has no usable rows: the symbol is unknown, or the data is old.Tries the next vendor in the chain.
VendorUnavailableErrorThe vendor did not answer: throttled, down, or a network error. It said nothing about the symbol.Tries the next vendor, and remembers that one vendor was unreachable.
VendorNotConfiguredErrorThe vendor needs a key or a setting that you did not set.Tries the next vendor.

How to read this table: each row is one class. The last column is the reaction inside the loop over the chain (router.py:232 to 260).

When no vendor returned data, the router returns a sentinel or raises. A sentinel is a fixed text in the place of data: it tells the model what happened, and not to invent a value.

The result of a chain that returned no data depends on which errors occurred, in this order
RuleCondition after the loopResultWhere
1at least one vendor raised VendorUnavailableErrorsentinel DATA_UNAVAILABLErouter.py:265
2one vendor raised an untyped error, and another raised NoMarketDataErrorsentinel DATA_UNAVAILABLErouter.py:267

How to read this table: take the first rule from the top whose condition is true. Rule 1 comes before rule 3 because a vendor that did not answer said nothing about the symbol. The run must not report "no data for NVDA" when the real problem was the network.

Rule 5 is the only case where a tool raises, and that ends the run. The two optional categories of rule 4 add context only (router.py:89 to 94).

8. Wrong idea corrected: the router does not try Alpha Vantage when Yahoo fails

Common wrong idea

Wrong: "The router knows two vendors for prices. If Yahoo fails, the router tries Alpha Vantage automatically."

Correct: the router tries exactly the vendors in the chain of the setting, in that order. The default chain for prices is "yfinance" alone, so a Yahoo failure gives a sentinel, and Alpha Vantage is never called. To get the fallback, set the chain to "yfinance,alpha_vantage".

Why the wrong idea fails: an earlier version did try every known vendor. Then a run mixed data from two sources that did not agree, and did not say so (comment at router.py:211 to 215). Only the word "default" in a setting means "all known vendors" (lines 216 to 225).

Limits of part B
  • I did not run a vendor function. The behaviour of Yahoo Finance for NVDA on these dates is not on this page.
  • The fundamentals chain is different: "sec_edgar,yfinance" (default_config.py:163). SEC EDGAR serves statements as filed. It needs the variable SEC_EDGAR_USER_AGENT in .env, with your name and email address (vendors/sec_edgar.py:98 to 101). Without it, the chain continues to Yahoo.
  • The Sentiment Analyst is the exception to "analysts call tools". It fetches StockTwits and Reddit posts itself before it calls the model (sentiment_analyst.py:66 to 76).

Part C: settings, files on disk, and tests

The short answer for part C

Every setting is a key in one dictionary, DEFAULT_CONFIG. Environment variables with the prefix TRADINGAGENTS_ replace the defaults. A run writes a report folder, a state file, one entry in the memory log, and a cache of prices. The tests never reach the network.

10. More detail: three layers of settings, and one chat model per tier

The settings have three layers. Each layer is read by a different part of the code.

  1. The defaults, with the environment on top. build_default_config (default_config.py:77) builds the dictionary and then applies the table _ENV_OVERRIDES (line 10). Each row maps one environment variable (a named value in the shell that started the program) to one key. The file .env is loaded when the package is imported (tradingagents/__init__.py:12). A value is converted to the type of the default: "true" becomes True, and "2" becomes the integer 2. A wrong value raises at start (lines 41 to 75).
  2. The process-wide settings. set_config (dataflows/config.py:33) merges a dictionary into the global one. A nested dictionary such as data_vendors is merged one level deep, so a partial update keeps the other vendors.
  3. The run config. The router reads the settings with get_config() (config.py:65). This function first looks at the run config (the settings of the run in progress, stored in a Python ContextVar, config.py:13). The method propagate binds the settings of its graph for the length of the run (trading_graph.py:185). LangGraph carries the context into the tool calls. So two graphs with different vendor settings can run in one process, and each tool call reads the settings of its own graph.

Most keys have a variable: TRADINGAGENTS_ plus the key in capital letters, for example TRADINGAGENTS_MAX_DEBATE_ROUNDS. Three names differ: TRADINGAGENTS_MAX_RISK_ROUNDS, TRADINGAGENTS_LLM_BACKEND_URL and TRADINGAGENTS_CACHE_DIR. The vendor keys and holding_period_days have no variable. A backend URL is the address of the server that answers the model calls, for a local server or a relay.

Two keys, quick_think_backend_url and deep_think_backend_url, are read through a formatted string (factory.py:147 and 149), which a plain text search misses.

Each run writes to four places. The table uses the default paths and the run of part A.

How to read this table: each row is one file or folder, and the last column is the function that writes it. HHMMSS is the time of the save; the folder name comes from trading_graph.py:288. The function safe_ticker_component (dataflows/symbols.py:155) checks a ticker before it becomes part of a path. So a ticker like "../x" cannot write outside the directory.

The memory log entry of the example run starts with one tag line. With a rating of Overweight, the tag is:

[2026-09-23 | NVDA | Overweight | pending]

The word "pending" means that the outcome is not known yet. The Memory Log node of a later run performs the settlement. Settlement fetches the prices after the holding period, computes the return of the stock and of its benchmark, and scores the decision. Then the node asks the quick model for a reflection (a short lesson about the decision and its outcome). The node writes both into the entry (memory/settlement.py and memory/reflection.py).

The next run of NVDA sends the Portfolio Manager up to 5 settled entries of NVDA (memory/log.py:93 to 130). It also sends up to 3 lessons of other tickers. A run dated in the past receives only lessons that were settled by its trade date (line 107). So a backtest cannot learn from the future.

How a resume knows that the settings did not change

With checkpoint_enabled, the graph saves the state after each node under a thread id (the key of one saved run in the SQLite file). The id is a hash of the ticker, the date, and a signature of the run (graph/checkpointer.py:28). The signature contains the analysts, the two round counts, the asset type, and a fingerprint of the portfolio. It also contains a hash of all other settings except the paths and the retry budget (trading_graph.py:140 to 165). So a resume with another model or another vendor starts fresh, instead of a mix of two runs.

12. More detail: the test suite blocks the network and guards the layering

The suite has 84 test files with 907 test functions, counted with a Python script over the tests/ folder. The file tests/conftest.py applies rules to every test:

  • No network. A fixture replaces the socket functions with a function that raises (lines 60 to 77). It also replaces the HTTP function of the library that yfinance uses. A test that needs the network must carry the marker integration. The default run of pytest excludes that marker (pyproject.toml, section tool.pytest.ini_options).
  • Own folders. Before the package is imported, the fixture points the three paths of the table above to a temporary folder (lines 29 to 39). A test never reads or writes your real cache and memory log.
  • Blank settings. Every TRADINGAGENTS_ variable from your .env is set to the empty string before the import (lines 9 to 26). So the tests see the defaults of the repository, not yours.
  • Fresh settings per test. A fixture replaces the global settings dictionary with a copy of the defaults before and after each test (lines 120 to 135).

Four tests guard the structure of the code. They fail on changes that look harmless:

  • test_layering.py: only files under tradingagents/dataflows/ may import yfinance.
  • test_i18n_coverage.py: each of the 12 report agents must call get_language_instruction. A new report agent must be added to the list in that test.
  • test_prompt_integrity.py: an analyst's instruction must be a string, not a tuple from a trailing comma. An analyst must not be asked for a trade call. A missing report must be presented as missing.
  • test_risk_router_path_map.py: the two path maps of section 2 must contain every value that the two conditional edges can return.

The continuous integration workflow runs the suite on Python 3.11, 3.12, 3.13 and 3.14 (.github/workflows/ci.yml). It runs one more time with the time zone of New York, so a test that passes only in UTC fails there. A second job installs the package without the development extras and imports it, so a missing dependency is found. A third job runs the linter ruff over the whole repository.

15. Recap, glossary, and sources

Recap
  1. One run passes one state dictionary through a graph of 12 agent nodes and 1 memory node: 13 node executions with the defaults.
  2. The four analysts run at the same time, each in its own subgraph with at most 20 tool rounds. The later agents read named fields of the state, not messages.
  3. Two counters end the debates: 2 × max_debate_rounds researcher turns, and 3 × max_risk_discuss_rounds risk turns.
  4. Every tool clamps its dates to the trade date, and the router tries only the configured vendor chain. A failure becomes a sentinel text, not a crash.
  5. Settings are one dictionary with 34 keys, replaced by TRADINGAGENTS_ environment variables. A run writes under ~/.tradingagents/.

Glossary

Analyst subgraph
A small graph of its own for one analyst, with a private message history. It returns only the report of that analyst.
Backend URL
The address of the server that answers the model calls.
Category
A group of tool methods that share one vendor setting. There are six.
Conditional edge
A function that reads the state and returns the name of the next node.
Debate round
One turn of each side of a debate: Bull and Bear, or Aggressive, Conservative and Neutral.
Environment variable
A named value in the shell that started the program. The file .env is loaded into these values at import.
Instrument context
The text with the company name, sector and exchange of the ticker, which every prompt receives.
Memory log
A text file with one entry per past decision. Later runs read its settled entries for lessons.
Model tiers
The two chat models of a run: the quick tier for analysts, researchers, risk analysts and trader, the deep tier for the two managers.
Node
One step of the graph: a Python function that reads the state and returns the fields that it changes.
Provider
The company or server that runs the chat model, such as OpenAI or a local server.
Rating
The result of a run: one of Buy, Overweight, Hold, Underweight, Sell. The word REVIEW marks a decision without a rating.
Reflection
A short lesson about a decision and its outcome, written by the quick model at settlement.
Run config
The settings of the run in progress, stored in a Python context variable, so that tool calls read the settings of their own graph.
Sentinel
A fixed text in the place of data. It tells the model what happened, and it tells the model not to invent a value.
Settlement
The step that fetches the prices after the holding period, computes the return of the stock and of its benchmark, and scores a decision.
State
The one dictionary that the graph passes from node to node, class AgentState.
Structured output
A model call that returns a typed object with named fields instead of free text.
Thread id
The key of one saved run in the SQLite checkpoint file: a hash of the ticker, the date and the signature of the settings.
Tool
A Python function with a description that the model can read and call. The model chooses the arguments.
Tool round
One answer of the model that asks for tools, followed by the results of those tools.
Trade date
The date of the analysis, the second input of a run. No tool serves data after it.
Vendor
An external data source with its own module under tradingagents/dataflows/vendors/.
Vendor chain
The list of vendor names in a setting, separated by commas, in the order to try.
