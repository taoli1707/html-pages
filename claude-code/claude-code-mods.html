What are Claude Code mods, and how does a mod change Claude Code from the inside?

Written 2026-10-07 · Reading time: about 29 minutes · You need to know: what Claude Code is, and what a JavaScript function is

The short answer

A mod is a Claude Code plugin that contains a JavaScript or TypeScript file with event handlers. Each time an event happens, Claude Code runs a handler, called a hook, inside its own process. An event is a tool call, a submitted prompt, or a part of the screen that is drawn. The hook can observe the event, rewrite it, or answer it instead of Claude Code.

The GitHub issue that you linked is the public proposal of this feature. Its author, an Anthropic engineer, posted it on 3 September 2026 under the name "function hooks". On 9 September 2026 the issue announced the product name "Claude Mods". On 1 October 2026 the issue said that mods are live. Mods are on by default in Claude Code version 2.1.287 and later. Your installed version is 2.1.290.

The comment that you linked is from a community member. It shows the first mod that draws an interactive surface: nine games above the prompt, playable while Claude works.

1. One example: a mod of 3 files counts tool calls and adds a /tally command

A mod is a Claude Code plugin that changes how Claude Code looks and behaves, with code that runs inside Claude Code. A plugin is a folder with a manifest file that Claude Code can install or load. A plugin can hold skills, commands, agents, and servers for the Model Context Protocol (MCP). A plugin becomes a mod when it also holds one code file with functions that react to what Claude Code does. The next paragraphs describe that file.

The example is the tutorial mod from the official documentation. It has three files. I created the three files in a temporary folder. Then I ran the validation command and the command of the mod, on 7 October 2026 with Claude Code 2.1.290.

first-mod/
├── .claude-plugin/
│   └── plugin.json       the manifest: name, version, description
└── hooks/
    ├── hooks.json        { "modules": ["./register.js"] }
    └── register.js       the hooks module

The file register.js does the work. It exports one function, register. Claude Code calls register one time when the mod loads, and passes it a function named on.

Each call of on adds one hook. A hook is a function that Claude Code runs when one named event happens. This file is the hooks module: the one JavaScript or TypeScript file that the plugin names in hooks/hooks.json, under the key modules. An event is one thing that Claude Code is about to do, together with its data. For example, a tool call is an event with the name of the tool and its arguments.

// first-mod/hooks/register.js
let calls = 0

export function register(on) {
  on('session.start', async ($, e, next) => {
    await $.command.register({ name: 'tally', description: 'Show how many tool calls Claude has made' })
    return next(e)
  })

  on('tool.call', async ($, e, next) => {
    calls += 1
    $.ui.invalidate('ui.render')
    return next(e)
  })

  on('command.run', { command: 'tally' }, async () => {
    return { text: 'Claude has made ' + calls + ' tool calls since this mod loaded' }
  })

  on('ui.render', { component: 'Spinner' }, async ($, e, next) => {
    return next({ ...e, props: { ...e.props, suffix: ' · tool calls: ' + calls + '…' } })
  })
}
Worked example: the mod runs through a session with 3 tool calls
  1. The session starts. Claude Code loads the mod and calls register(on). The four calls of on add four hooks. The variable calls is 0. The module runs one time at load. The hooks only wait until their event happens.
  2. The event session.start happens. The first hook runs. It calls $.command.register and adds the command /tally. Then it returns next(e). Only a hook can add a command. The call of next lets the session start as usual.
  3. You type a prompt. Claude calls the tool Bash. The event tool.call happens. The second hook runs: calls becomes 1. The hook asks Claude Code to redraw the screen, then returns next(e). The hook does not change the tool call. It passes the same event e on, so the tool runs as usual.
  4. Claude Code draws the spinner. The event ui.render with component: 'Spinner' happens. The fourth hook runs. It calls next with a copy of e that has one more property, suffix. The spinner shows "Thinking · tool calls: 1…". The hook rewrites the event. Claude Code draws its own spinner, but with the text that the hook added.
  5. Claude calls Read two more times. Steps 3 and 4 repeat. calls becomes 2, then 3. The spinner shows "tool calls: 3…". All four hooks share the variable calls, because they are in the same file.
  6. You type /tally. The event command.run happens with command: 'tally'. The third hook matches, runs, and returns an object with text. It does not call next. The transcript shows "first-mod: Claude has made 3 tool calls since this mod loaded". The hook answers the event itself. Nothing else handles /tally, so no Claude turn runs and no tokens are used.

My real run: I ran claude -p "/tally" --plugin-dir ./first-mod with no prior tool calls. The output was first-mod: Claude has made 0 tool calls since this mod loaded. The count is 0 because the non-interactive run made no tool calls before the command. The validation command listed the four hooks and the two API calls, see section 2.

2. The rule: a hook receives the event, the API, and a next function, and it chooses one of three actions

Every hook has the same signature: ($, e, next). The three arguments have fixed meanings.

  • $ is the mods API. The mods API is the one object through which a hook reaches anything outside its own code. This includes the screen, commands, files, processes, the network, and a model. Each call is a namespace and a method: $.ui.toast(text), $.fs.read(path), $.model.complete(...). The reference page lists 21 namespaces, from $.agent to $.ui.
  • e is the event. It is plain, frozen data. For tool.call with the tool Bash, e.tool is 'Bash' and e.command is the command text.
  • next is the next function. The next function passes the event to the other mods and then to the normal behaviour of Claude Code. It returns the result of the event, for example the output of the tool.

A hook chooses one of three actions with these arguments. The three actions are the whole model.

The three actions of a hook, with the line of code that performs each one
ActionWhat the hook doesCodeExample in section 1
ObserveNotes the event and lets it continue without change.return next(e)The tool.call hook counts and passes on.
RewriteChanges the event, then lets it continue.return next({ ...e, x: y })The ui.render hook adds suffix.
AnswerReturns its own result and never calls next. The normal behaviour does not run.return { text: '…' } or return { deny: '…' }The command.run hook returns the text.

How to read this table: each row is one action. The third column is the shape of the return statement. The highlighted row is the action that stops the normal behaviour.

A hook can also act after the event. It calls await next(e), receives the result, and then does something with the result. The example file tool-call.ts in the built-in skill does this. It runs the Bash tool. When the result has isError === true, it writes a status line with $.ui.status.

A matcher limits a hook to some events

The second argument of on is optional. It is a matcher: an object with field values that the event must have. The hook on('command.run', { command: 'tally' }, …) runs only when the command is tally. The hook on('ui.render', { component: 'Spinner' }, …) runs only when Claude Code draws the spinner. It does not run for a pane or a tool row. Without a matcher, the hook runs for every event of that name.

Claude Code reads the code before it runs the code

Claude Code analyses the source of the hooks module statically when it loads the mod. It finds every on call and every $ call. The command claude plugin validate runs the same analysis. For the example mod, my run printed these two lines:

❯ ./register.js hooks: session.start, tool.call, command.run{command=tally}, ui.render{component=Spinner}
❯ ./register.js calls: $.command.register, $.ui.invalidate

This is why the code has rules. The event name in on must be a string literal. Each API call must be written in full as $.namespace.method. The code may not copy $ into a variable. If the analysis cannot find a hook, Claude Code does not call it. The benefit: you can list what a mod does before you install it, and you do not need to run it.

3. Several mods form one chain, and the first mod in the chain controls the others

When several mods hook the same event, their hooks form a middleware chain. A middleware chain is a sequence of functions. Each function calls the next one through next, and the last call reaches the normal behaviour. The issue compares this to the web frameworks Express and Koa, which use the same pattern. The first mod is the outermost: it sees the event before the others, and it sees the result after them. If the first mod does not call next, the others never run.

The documentation gives this order of the chain, from outermost to innermost:

  1. The built-in guard mod sec-default, where it loads, then the mods that your organization lists first in managed settings.
  2. The mods that you installed. Among them, a mod runs before the mods that it lists under dependencies. Inside one module, hooks run in the order of the on calls.
  3. The mods that your organization lists last in managed settings.
  4. The other built-in mods, for example diff.

The consequence for an organization: an administrator puts a policy mod first. The policy mod can remove methods from $ or answer an event with deny, and no later mod can undo this. The issue describes this in its fourth video: "Admins can remove affordances from $ so that all plugins below cannot invoke that side-effect."

A second example: the community mod from the comment draws a game above the prompt

The comment that you linked, posted on 14 September 2026 by a community member, is a data point in the issue. It presents the mod cc-arcade: nine games and a pet, drawn above the prompt, playable while Claude works, with zero tokens. The comment names the events and methods that the mod uses. The side-by-side comparison shows how the two examples use the same mechanism for different purposes.

first-mod (official tutorial)

Hooks ui.render with the matcher Spinner and rewrites the props of the spinner that Claude Code draws.

Keeps its count in a module variable. The count resets at each reload.

cc-arcade (community, from the comment)

Hooks ui.render with the matcher AbovePrompt and returns its own tree of elements: the game board and buttons.

Keeps best scores and the pet in $.store, so they survive restarts. Pauses the game on turn.complete and feeds the pet on tool.call.

The principle: the same event, ui.render, serves both a small rewrite and a full replacement. The matcher selects which part of the screen the hook touches. The comment also reports three undocumented facts that cost its author time. A local variable may not be named h in a drawing module. The paths of Client modules must be string literals. The band above the prompt is about half the terminal and redraws about ten times a second.

The last fact matches the documented limit of 10 redraws per second in section 5.

4. A mod differs from a settings hook in one main point: it runs inside the Claude Code process

Claude Code had hooks before mods. A settings hook is a shell command, a web request, or a prompt that you configure in a settings file. Claude Code runs it on a lifecycle event such as PreToolUse. The documentation uses "hook" for the function of a mod, and "settings hook" for the older kind. The table compares the four ways to extend Claude Code, following the comparison table of the documentation.

How to read this table: each column is one way to extend Claude Code. Read a row across to compare. The highlighted row is the main difference. One plugin can hold all four kinds.

Where a mod runs matters for drawing. The hooks of a mod run in every kind of session that loads the plugin. The drawing appears only in the terminal and in the Code tab of the Desktop app. In the chat panel of the Visual Studio Code extension, in claude -p, and in a cloud session, the hooks run but nothing is drawn. In a WSL session of the Desktop app, mods do not run at all.

5. The limits: 10 seconds per hook, 4 MiB per store, 10 redraws per second

The reference page gives fixed limits. Claude Code skips a hook that exceeds a time limit, and rejects a call that exceeds a size limit. The table shows the limits that affect a first mod.

One consequence of the 10 second limit: a hook that waits for a slow network call must do that call through $.http or $.process. Time inside an API call does not count. A hook that computes for 11 seconds in its own code is skipped.

The issue also names the design in one sentence that uses the vocabulary of functional programming: an effect-parameterized endomorphic continuation model for plugins. In plain words: each hook is a function from an event to an event of the same type (endomorphic). It receives the rest of the chain as a function (continuation). Every side effect passes through the $ parameter (effect-parameterized). The author also wrote that the $ symbol is not negotiable, with a link to the library jQuery, which made that symbol famous.

7. Wrong idea corrected: a mod runs with your permissions and is not sandboxed

Common wrong idea

Wrong: "A mod only reaches the world through $, so Claude Code sandboxes it. A mod from an unknown author is safe to try."

Correct: the documentation says that mods are not sandboxed. A mod runs with your permissions inside Claude Code. It can read and write files anywhere your account can. It can start programs and make network requests. It can read environment variables and settings files, including an API key. It can see every prompt and tool call, approve a tool call before you are asked, and call a model on your plan.

Why the wrong idea fails: the $ object makes the actions of a mod visible, not restricted. Static analysis lists what the mod calls. The restriction exists only when an outer mod, such as the guard of an organization, removes methods from $. On your own machine with no managed settings, no guard loads. So read the output of claude plugin validate before you install a mod, and install only from authors that you trust. The one thing that a mod cannot change is the permission prompt itself.

9. Words that you will hear

These terms belong to the work with mods, but not to the event model that this page explains.

Pane, band, AbovePrompt
A pane is a view beside the transcript, opened with $.ui.open. A band is a row above the prompt, drawn by a hook on ui.render with the matcher AbovePrompt. Both are results of the rewrite or answer action on ui.render.
Surface
The place where Claude Code draws: terminal, desktop, vscode, or mobile. A drawing hook asks $.ui.resolve(e) for the elements of the current surface.
$.state and $.store
Two places to keep values. $.state keeps values for the session and survives a reload of the mod. $.store keeps values across sessions on the machine, up to 4 MiB. A plain variable in the module resets at each reload.
Hot reload
Claude Code watches a folder loaded with --plugin-dir, or the folder of mods that Claude wrote in the session. It reloads the module when a file changes. A reload runs register again and fires session.start again.
--plugin-dir and the marketplace
claude --plugin-dir ./first-mod loads a folder for one session without installation. An installed mod comes from a marketplace: claude plugin install name@marketplace. An installed copy is cached by version, so edits need a new version number.
The plugin-authoring skill and the dev-mods folder
When you ask Claude for a mod in a session, Claude uses the built-in skill plugin-authoring. Claude writes the mod under ~/.claude/dev-mods/ followed by the session ID. Claude Code then asks you once whether to enable hot reloading for the session. Claude Code deletes that folder after the cleanup period of your settings.
claude plugin test
Runs automated tests of a mod from the shell, without a session or network. A test fires events through $ and checks what the hooks did. One test may take 5 seconds unless it sets a longer timeout.
sec-default and managed settings
The built-in guard mod. It loads first on a machine with managed settings or in a Team or Enterprise organization. It keeps the classic hooks, prompt content, and deny rules of the organization out of reach of the mods that a person installs.

10. Check your understanding

Try to answer before you open each answer.
  1. A hook on tool.call with the matcher { tool: 'Edit' } returns { deny: 'protected file' } for every path that ends in .env. Which of the three actions is this, and does the tool run?
    Show the answer

    Answer. The tool does not run.

    The hook returns its own result and never calls next, so the chain stops at this hook. Nothing after it, including the normal behaviour that runs the tool, executes. A typical wrong answer is "rewrite", but a rewrite always calls next with a changed event. See section 2.

  2. Two mods hook tool.call: a mod that your organization lists first in managed settings, and a mod that you installed. Your mod approves every tool call. Can your mod approve a call that the organization mod denied?
    Show the answer

    No.

    The organization mod is outermost. It sees the event first. When it answers with deny, it does not call next, so your mod never runs for that event. A later mod cannot stop an earlier mod from seeing an event, and cannot undo its answer. See section 3.

  3. You change the text in the ui.render hook of first-mod while the session runs with --plugin-dir. After the reload, /tally prints 0 although Claude made 5 tool calls before the edit. Why?
    Show the answer

    A reload runs register again, and the module variables start over. The variable calls is a module variable, so it becomes 0. To keep a value across reloads, the mod must store it in $.state or $.store. See section 9.

  4. You want to log every tool call to a file with a shell script that you already have, and you need nothing on the screen. Do you write a mod or a settings hook?
    Show the answer

    A settings hook.

    The comparison table says: choose a settings hook when you want to block, allow, or log an event with a script that you already have. A mod is the right choice when you need a pane, a band, a command, or a rewrite of an event. Both can see every tool call. See section 4.

11. Recap, glossary, and sources

Recap
  1. A mod is a plugin with a hooks module. The module exports register(on), and each on call adds a hook for one event, with an optional matcher.
  2. Every hook receives ($, e, next). It observes with next(e), rewrites with next({ ...e, change }), or answers with its own result and no call of next.
  3. Hooks on one event form a middleware chain. The outermost mod, which is the guard or the first policy mod of the organization, controls whether the inner mods run.
  4. A mod reaches the outside only through $, so static analysis can list its hooks and calls before you run it. But a mod is not sandboxed: it runs with your permissions.
  5. The issue proposed the feature on 3 September 2026 as "function hooks". The product name became "Claude Mods" on 9 September. Mods shipped on 1 October 2026, on by default from version 2.1.287.

Glossary

Event
One thing that Claude Code is about to do, together with its data. Example: a tool call with the name of the tool and its arguments.
Hook
A function in a hooks module that Claude Code runs when one named event happens. On the documentation pages, "hook" means this function, and the older kind is a "settings hook".
Hooks module
The one JavaScript or TypeScript file that a plugin names in hooks/hooks.json under modules. It exports register.
Matcher
The optional second argument of on: an object with field values that the event must have for the hook to run.
Middleware chain
A sequence of functions where each function calls the next one through next, and the last call reaches the normal behaviour.
Mod
A Claude Code plugin that changes how Claude Code looks and behaves, with code that runs inside Claude Code.
Mods API ($)
The one object through which a hook reaches anything outside its own code, organized as namespaces with methods.
Next function (next)
The third argument of a hook. It passes the event to the other mods and then to the normal behaviour, and returns the result.
Plugin
A folder with a manifest file that Claude Code can install or load. It can hold skills, commands, agents, MCP servers, and a hooks module.
Settings hook
A shell command, a web request, or a prompt that you configure in a settings file and that Claude Code runs on a lifecycle event.
