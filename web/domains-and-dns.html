How do a domain name and DNS connect a visitor to the website that you create?

Written 2026-10-13 · Reading time: about 24 minutes · You need to know: what an IP address is, and that a web server answers requests

The short answer

A visitor types a name, but the network needs an address. DNS (the Domain Name System) is the public directory that turns the name into the address. When you create a website, you do three separate things. You rent the name from a registrar. You publish records in DNS that map the name to an address. And you run a web server at that address.

Example: a lookup of example.com on 13 October 2026 asked three groups of servers in order. First the root servers, then the servers of the .com registry, then the two name servers of the domain. The final answer was the address 172.66.147.243, valid for 300 seconds.

The time that a change needs to reach visitors is not "48 hours". It is the TTL (time to live) of the old record, which you can set. For an address record a TTL of 300 seconds is common. The 48 hours come from the TTL of the delegation record in the .com registry, which only matters when you change name servers.

Assumptions on this page
  • You create a static website on a hosting service, for example GitHub Pages, and you want your own name for it. The steps are the same for any host that gives you an IP address or a host name.
  • The page covers the path from the name to the address. It does not cover HTTPS certificates or the web server itself.

1. One real lookup: example.com needs three questions and ends at 172.66.147.243

A domain name is a name such as example.com, written as labels from right to left: first com, then example. The rightmost label is the top-level domain (TLD), for example com, org, or de. A browser cannot send a request to a name. It needs an IP address, a number such as 172.66.147.243 that identifies one machine on the internet. DNS (the Domain Name System) is the public, distributed directory that maps names to addresses.

The example below is a real lookup. I ran the tool dig with the option +trace on 13 October 2026 at 04:08 UTC. This option shows every question that a full lookup asks. The lines in the steps are copied from the output.

Worked example: the lookup of example.com, as run
  1. Ask a root server: "Who knows com?" The answer is a list of 13 names, a.gtld-servers.net to m.gtld-servers.net. Output line: com. 172800 IN NS a.gtld-servers.net. A resolver is the server that performs the lookup for the visitor and caches the answers. A root server is a server whose addresses every resolver knows in advance. There are 13 root server names, and on 13 October 2026 they ran on 2,047 machines worldwide (source 3). A root server does not know example.com. It only knows which servers hold the list for each top-level domain.
  2. Ask a .com server: "Who knows example.com?" The answer is two names: hera.ns.cloudflare.com and elliott.ns.cloudflare.com. Output line: example.com. 172800 IN NS hera.ns.cloudflare.com. The .com servers belong to the registry of .com. The registry is the organisation that keeps the list of all .com names. For .com the registry is Verisign (source 4). The registry stores only one thing for each name: the NS record, which names the servers that hold the real records. This hand-over is called a delegation.
  3. Ask a name server of the domain: "What is the address of example.com?" The answer is two addresses. Output lines: example.com. 300 IN A 172.66.147.243 and example.com. 300 IN A 104.20.23.154. These two servers are the authoritative name servers of example.com. They hold the records that the owner of the name wrote. An A record maps a name to an IPv4 address. Two A records mean two addresses; the browser can use either.
  4. Read the TTL. The number 300 in the last answer is the TTL (time to live). The TTL is the number of seconds for which a server may keep the answer and reuse it. Here: 300 seconds, that is 5 minutes. The standard RFC 1035 defines the TTL in the same way. It is the time interval that the record may be cached before the source is consulted again (source 2).

Result: three questions, in the order root, registry, authoritative name server. The browser then sends its request to 172.66.147.243.

The visitor's computer does not ask these three questions itself. It asks one resolver, and the resolver asks the three questions. In my run, the resolver was the home router at 192.168.1.1. A second lookup of example.com, without +trace, took 8 milliseconds and returned the TTL 121. The resolver had the record from an earlier question, and 179 of the 300 seconds had passed.

2. The rule: four parties each hold one piece of the path

The lookup works because each party stores exactly one piece. A registrar is a company that sells domain names to the public and has a contract with the registry. When you create a website, you meet the four parties in the order of the table below.

Four parties, and the one piece of the path that each one holds

RegistrarYour contract for the name, and the NS records that it sends to the registryBuy the name. Enter the names of your name servers.Any ICANN-accredited company (source 5)
RegistryThe list of all names in one TLD, with the NS records of each nameNothing directly. The registrar talks to the registry for you.Verisign for .com
Authoritative name servers (your DNS host)Your records: A, CNAME, MX, and othersCreate the records that point to your web host.hera.ns.cloudflare.com
Web hostYour files, at an IP addressUpload the site. Tell the host your domain name.GitHub Pages at 185.199.108.153

How to read this table: each row is one party. Read the rows from top to bottom: that is the order in which a lookup visits them. The highlighted row is where you spend most of your time.

ICANN, the organisation that coordinates the name system, accredits registrars. The ICANN page defines an accredited registrar as an entity that offers registration services to registrants with direct access to the registries (source 5). The registrar and the DNS host are often the same company, but they are two roles. You can buy the name at one company and run the records at another. The link between them is the NS record in the registry.

3. Your setup: four A records and one CNAME record connect myshop.com to GitHub Pages

Now the same path from your side. Suppose that you bought myshop.com (an example name) and your site is on GitHub Pages at yourname.github.io. GitHub documents the records that it needs (source 6). The steps below use those values.

Worked example: the records for myshop.com
  1. At the registrar, set the name servers. If you use the DNS service of the registrar, the registrar does this for you. If you use another DNS host, you enter its server names, for example the two Cloudflare names from section 1. The registrar sends these names to the registry as the NS records of myshop.com. From now on, every lookup for your name is sent to these servers.
  2. At the DNS host, create A records for the apex. The apex is the bare name myshop.com without any label in front. GitHub Pages lists four addresses: 185.199.108.153, 185.199.109.153, 185.199.110.153, 185.199.111.153. Create one A record for each. Four records give four addresses. If one machine fails, the browser can use another. On 13 October 2026, a lookup of taoli1707.github.io returned exactly these four addresses, so GitHub still uses them.
  3. At the DNS host, create a CNAME record for www. A CNAME record maps a name to another name, not to an address. Create www.myshop.com → yourname.github.io. The resolver then does a second lookup for yourname.github.io and uses its addresses. If GitHub changes its addresses, your www name follows automatically. Real example from the same run: www.github.com. 3053 IN CNAME github.com.
  4. At the web host, declare the domain. In the repository settings of GitHub Pages, enter myshop.com as the custom domain. One web server serves many sites at one address. It chooses the site by the name in the request. Without this step, the address is correct but the server does not know which site to show.
  5. Verify with dig. Run dig myshop.com +noall +answer and dig www.myshop.com +noall +answer. The first must show the four A records. The second must show the CNAME record and then the A records of yourname.github.io. The output shows what the resolver sees, not what you typed in a form. A typing error in a record is visible here within one TTL.

Compare the two record types

A record

Name → IPv4 address. Example: myshop.com → 185.199.108.153.

Allowed at the apex. If the host changes its address, you must change the record.

CNAME record

Name → other name. Example: www.myshop.com → yourname.github.io.

Not allowed at the apex. If the host changes its address, nothing changes for you.

The principle after the comparison: use a CNAME record for every name that points to a service. Use an A record only where a CNAME record is not allowed. The standard RFC 1034 gives the reason for the apex rule. If a CNAME record is present at a node, no other data should be present (source 1). The apex must hold the NS records and other records, so it cannot hold a CNAME record.

Some DNS hosts offer an ALIAS or ANAME record that behaves like a CNAME record at the apex; GitHub names both (source 6). This is a feature of the host, not of the standard.

4. The data: the address record expires after 5 minutes, the delegation after 48 hours

Every answer in section 1 carried a TTL. The TTL decides how long a resolver reuses an answer. Therefore the TTL also decides how long a change needs to reach a visitor.

Guess first

You change the A record of your apex from one address to another. Your DNS host had set the TTL to 300 seconds. What is the longest time until every visitor sees the new address? Choose before you continue: 5 minutes, 24 hours, or 48 hours.

Answer to the guess: 5 minutes. A resolver that cached the old A record keeps it for at most 300 seconds. After that it asks your name servers again and receives the new address. The 48 hours apply only to the NS records in the registry, that is, when you move to another DNS host.

5. Wrong idea corrected: a change is visible after the old TTL, not after 48 hours

Common wrong idea

Wrong: "DNS changes take 24 to 48 hours to propagate. Nothing can be done about it."

Correct: a resolver keeps the old record for at most its TTL. After the TTL, the resolver asks again and receives the new record. For an A record with a TTL of 300 seconds, every visitor sees the change within 5 minutes. Nothing is pushed to resolvers; each resolver only forgets the old answer.

Why the wrong idea fails: the number 48 hours is real. But it belongs to the NS records in the registry, which had a TTL of 172,800 seconds in the run above. It applies when you change your name servers, not when you change a record at your DNS host. GitHub writes "DNS changes can take up to 24 hours to propagate" (source 6). That is a safe upper limit for any record and any TTL, not a measured delay.

A practical consequence: before you plan a change, lower the TTL of the record to 300 seconds, and wait for the old TTL to pass. Then make the change. Visitors see the new value within 5 minutes. After the change you can raise the TTL again, so resolvers ask your servers less often.

6. Limits: what this page does not cover

Limits
  • HTTPS is a separate step. A correct DNS record makes the browser reach your server. A certificate makes the connection encrypted and shows the lock symbol. GitHub Pages issues a certificate after the DNS records are correct, and writes that this can take up to 24 hours (source 6).
  • One run, one machine. The TTL and address values are from one run on 13 October 2026 behind one home resolver. The values of example.com can change. The structure of the lookup does not.
  • The resolver was not traced. dig +trace asks the servers itself, in place of the resolver. A real resolver may already hold some answers and then skips those questions.
  • Other record types exist. MX records (mail), TXT records (verification and mail policy), and AAAA records (IPv6 addresses) follow the same rules. They are not part of the path to a website.
  • The number of root instances changes daily. The value 2,047 is the count that root-servers.org showed on 13 October 2026.

7. Words that you will hear

These terms appear in registrar and hosting interfaces. They are not needed for the main path.

AAAA record
The IPv6 form of an A record: name → IPv6 address. GitHub Pages lists four of them next to the four A records.
DNSSEC
Signatures on DNS records, so that a resolver can detect a forged answer. It is switched on at the registrar and the DNS host together. It does not change the path on this page.
Propagation
The word that hosting interfaces use for the wait until every resolver has dropped the old record. It is the TTL of section 4, not a process that pushes data.
Subdomain
A name with one more label in front, for example www.myshop.com or blog.myshop.com. Each subdomain has its own records at your DNS host, at no extra cost from the registrar.
WHOIS and RDAP
Two public services that show who registered a name and which name servers it uses. The IANA record of .com lists both servers for Verisign (source 4). Use them to check that the registrar sent the right NS records to the registry.
Zone
The set of all records of one domain at its authoritative name servers. "Edit the zone" means "edit your records".

8. Check your understanding

Try to answer before you open each answer.
  1. You bought myshop.com at a registrar and uploaded the site to a host at 203.0.113.10 (an example address). A visitor gets "server not found". Which of the four parties did you skip?
    Show the answer

    The authoritative name servers: no A record exists.

    The registrar holds the contract and the registry holds the NS records, but nobody wrote the record that maps myshop.com to 203.0.113.10. The lookup reaches your name servers in step 3 of section 1 and receives no address. A typical wrong answer is "the web host", but the host cannot be reached before the name has an address. See section 2.

  2. Your A record has a TTL of 3,600 seconds. At 10:00 you change the address. A visitor looked the name up at 09:50 through a resolver. At what time does that resolver certainly use the new address?
    Show the answer

    At 10:50 at the latest.

    The resolver cached the old record at 09:50 with a TTL of 3,600 seconds, that is 60 minutes. The record expires at 10:50. The next question after 10:50 goes to your name servers and receives the new address. A typical wrong answer is 11:00. That answer counts the TTL from the time of the change. But the TTL counts from the time of the cached answer. See section 4.

  3. Why can you not create the record myshop.com CNAME yourname.github.io, while www.myshop.com CNAME yourname.github.io is fine?
    Show the answer

    Because the apex must hold other records, and a CNAME record forbids other records at the same name.

    RFC 1034 states that if a CNAME record is present at a node, no other data should be present. The apex myshop.com must hold at least the NS records of the domain. www.myshop.com holds nothing else, so a CNAME record is allowed there. Use A records at the apex, or an ALIAS record if your DNS host offers one. See section 3.

9. Recap, glossary, and sources

Recap
  1. A lookup asks three questions in order. It asks a root server, then a registry server of the top-level domain, then an authoritative name server of the domain. Each answer names the next server.
  2. Four parties each hold one piece. The registrar holds the contract and sends the NS records. The registry holds the delegation. Your DNS host holds your records. Your web host holds the files.
  3. For a site on GitHub Pages, you create four A records at the apex and one CNAME record for www. Then you declare the domain at the host.
  4. A change is visible after the TTL of the old record. For an A record with a TTL of 300 seconds that is 5 minutes. The 48 hours belong to the NS records in the registry.

Glossary

A record
A DNS record that maps a name to an IPv4 address.
Apex
The bare domain name without any label in front, for example myshop.com.
Authoritative name server
A server that holds the records of a domain as its owner wrote them. The answers of all other servers are copies.
CNAME record
A DNS record that maps a name to another name. The resolver then looks the other name up.
Delegation
The hand-over from a registry to the authoritative name servers of a domain, stored as NS records.
DNS (Domain Name System)
The public, distributed directory that maps domain names to IP addresses and other data.
Domain name
A name such as example.com, made of labels, with the top-level domain at the right end.
IP address
A number such as 172.66.147.243 that identifies one machine on the internet.
NS record
A DNS record that names the authoritative name servers of a domain.
Registrar
A company that sells domain names to the public and has a contract with the registry.
Registry
The organisation that keeps the list of all names in one top-level domain, with the NS records of each name.
Resolver
A server that performs the full lookup on behalf of a visitor and caches the answers.
Root server
One of 13 named servers, known to every resolver in advance, that hold the NS records of every top-level domain.
Top-level domain (TLD)
The rightmost label of a domain name, for example com.
TTL (time to live)
The number of seconds for which a server may keep and reuse a DNS answer.
